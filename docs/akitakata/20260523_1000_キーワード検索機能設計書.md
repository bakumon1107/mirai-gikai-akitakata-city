# キーワード検索機能 設計書

作成日: 2026-05-23

---

## 1. 何を作るか（概要）

ユーザーが「防災」「子育て」「道路」などのキーワードを入力すると、サイト内のすべてのコンテンツを横断して関連情報を一覧で表示する機能。

現在はコンテンツが「議案」「一般質問」「記者会見」「地域懇談会」とページ別に分かれており、横断的に調べる手段がない。検索機能を入れることで「この市でいつ・誰が・何を議論したか」をすぐ引ける状態になる。

---

## 2. 検索対象コンテンツ

| コンテンツ種別 | 表示名 | 検索対象フィールド |
|---|---|---|
| 議案 | 議案 | AI解説タイトル、AI要約、議案タグ |
| 一般質問 | 一般質問 | 質問者名、質問トピック、AI要約 |
| 市長記者会見 | 記者会見 | 会見タイトル |

> **対象から外すもの（理由）**
> - 地域懇談会の意見 → 個別の遷移先ページがないため対象外。将来ページができたタイミングで追加する。
> - 議案の原文PDF → テキスト量が膨大で精度が落ちる。将来課題。
> - 一般質問の生テキスト → AI要約が既にあるので、要約を対象にする方が品質が高い。

## 3. UI設計

### 3-1. 検索の入口

**ヘッダーに検索アイコンを配置する案**

```
┌─────────────────────────────────────────────────────┐
│  みらい議会 安芸高田          [🔍]  ≡メニュー       │
└─────────────────────────────────────────────────────┘
```

アイコンをタップすると検索バーが展開する（または `/search` ページへ遷移する）。

> **なぜヘッダーか**: どのページにいても検索を起動できる。トップページだけに置くと「そこに戻らないと検索できない」と気づかれにくい。

## 5. 検索の仕組み（技術方式）

### 方式比較

| 方式 | メリット | デメリット |
|---|---|---|
| A: Supabase の `ILIKE` 検索 | 追加コスト0、実装シンプル | 「防災」で「ぼうさい」はヒットしない。部分一致のみ |
| B: Supabase の全文検索（`pg_bigm`） | 日本語の分かち書きに対応、精度が高い | DBに拡張追加が必要 |
| C: 外部サービス（Algolia等） | 検索精度が高い、UIコンポーネントも充実 | 月額コストが発生、外部依存が増える |

**推奨: まずAで作り、使われるようになったらBへ移行**

- データ量が現状少ない（議案〜200件、質問〜100件）ので `ILIKE` でも実用的に動く
- Supabase の REST API で `&name=ilike.*防災*` の形で実現可能
- 将来的に「ひらがなで入力してもヒットしてほしい」等の要望が出たらBへ移行する

## 8. セキュリティ設計

### 8-1. SQLインジェクション対策

**このプロジェクトは構造上、SQLインジェクションが発生しない。**

既存コードはすべて Supabase JS クライアントのメソッドチェーン（`.ilike()`, `.eq()`, `.gte()` 等）でクエリを組み立てている。これらのメソッドは内部でパラメータ化クエリ（プリペアドステートメント）を使うため、ユーザー入力がそのままSQL文字列に埋め込まれることはない。

```typescript
// ✅ 安全: Supabase クライアントのメソッドを使う（パラメータ化クエリ）
supabase
  .from("bill_contents")
  .select("id, title, summary")
  .ilike("title", `%${keyword}%`)   // keyword がどんな文字列でもSQLとして解釈されない
```

**禁止パターン（やってはいけないこと）:**

```typescript
// ❌ 危険: 文字列結合でSQL文を作ってrpc()に渡す
supabase.rpc("search_bills", { query: `SELECT * WHERE title LIKE '%${keyword}%'` })

// ❌ 危険: テンプレートリテラルで生SQL
supabase.from("bills").select("*").filter("name", "ilike", `%${keyword}%`) // これはOK
// ↑ filter() はメソッドなので安全。ただし以下は危険:
// supabase.rpc("exec_sql", { sql: `... '${keyword}'` })
```

検索機能の実装では `.ilike()` メソッドのみを使い、`.rpc()` に文字列結合したSQLを渡すことを禁止する。

---

### 8-2. 入力バリデーション（Server Action / Loader 側）

ユーザー入力は必ずサーバー側で検証してからDBに渡す。

| チェック項目 | 内容 | 実装場所 |
|---|---|---|
| 空白のみ | トリムして空なら検索しない | Server Action |
| 長さ上限 | 100文字超はエラーを返す | Server Action |
| 許容文字 | 制御文字（`\0`, `\n` 等）を除去 | Server Action |

```typescript
// バリデーション例（Server Action 内）
function validateSearchQuery(raw: string): string | null {
  const q = raw.trim().replace(/[\x00-\x1F\x7F]/g, ""); // 制御文字除去
  if (q.length === 0 || q.length > 100) return null;
  return q;
}
```

> **なぜ100文字か**: 実用的な検索ワードで100文字を超えることはほぼない。超える場合はスクレイピングや異常リクエストの可能性が高い。

---

### 8-3. XSS（クロスサイトスクリプティング）対策

**Next.js のJSXレンダリングがデフォルトでエスケープを行うため、追加対応は不要。**

検索キーワードや検索結果のテキストをそのまま `{keyword}` や `{result.title}` の形でJSXに埋め込めば、`<script>` などはエスケープされて文字列として表示される。

ただし以下は禁止:

```typescript
// ❌ 危険: dangerouslySetInnerHTML にユーザー入力・DB取得値を渡す
<div dangerouslySetInnerHTML={{ __html: result.summary }} />

// ✅ 安全: JSX に直接渡す
<div>{result.summary}</div>
```

---

### 8-4. 過剰リクエスト対策（レートリミット）

検索は1回のキー入力ごとにDBアクセスが走る可能性があるため、以下の制御を入れる。

| 対策 | 内容 |
|---|---|
| デバウンス | 入力が止まってから300ms後に検索実行（クライアント側） |
| 最低文字数 | 1文字では検索しない（2文字以上で実行） |
| Supabase RLS | 万が一クライアントから直接APIを叩かれても、RLS有効のため公開データ以外は取得不可 |

> 現状のデータ量（〜数百件）ではサーバー過負荷のリスクは低い。将来的に必要になればNext.jsのミドルウェアやVercelのEdge Rate Limitingで追加対応する。

---

### 8-5. URLパラメータの扱い

検索結果は `/search?q=防災` のURLで表現する。`q` パラメータは表示前にバリデーション済みの値のみを使う。

```typescript
// page.tsx: searchParams から取得してバリデーション
const rawQ = searchParams.q ?? "";
const keyword = validateSearchQuery(rawQ);
if (!keyword) redirect(routes.search()); // 不正入力は空の検索ページに戻す
```
