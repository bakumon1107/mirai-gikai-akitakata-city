## 1. `bill-registration-akitakata` — セッションID更新ガイド追加

### 現状の問題

固定値テーブル（セッションID・委員会ID）は定例会ごとに手動追記が必要だが、**いつ・どこを・どうやって更新するか**の案内がない。次の定例会追加時に忘れる。

### 改善内容

`## 固定値` セクションの冒頭に以下を追記する。

```markdown
> **新定例会を追加するたびに、このテーブルを更新すること。**
> セッションIDはDBから取得する（手順は「セッションID取得方法」を参照）。
```

セッションID取得コマンドを追記する:

```bash
# 全セッション一覧（slug, id, name）を取得
source .env.production && curl -s \
  "$SUPABASE_URL/rest/v1/council_sessions?select=slug,id,name&order=created_at.desc" \
  -H "apikey: $SUPABASE_SERVICE_ROLE_KEY" \
  -H "Authorization: Bearer $SUPABASE_SERVICE_ROLE_KEY" | python3 -m json.tool
```

### 実施ファイル

`.claude/skills/bill-registration-akitakata/SKILL.md` の `## 固定値` セクション先頭に追記。

## 2. `db-access` — 廃止・CLAUDE.md統合

### 廃止理由

- 内容が30行と薄く、スキルとして呼び出す価値より CLAUDE.md の常時参照のほうが安全
- `general-questions` スキルからは「db-access スキルの接続情報を使用」と参照されているが、実質コマンド1行の情報
- スキルとして独立させると「呼び出し忘れ」で接続ルールを見落とすリスクがある

### 移行先

CLAUDE.md の `## Supabase & Environment Notes` セクションに以下を追記する:

```markdown
### DB直接操作の規約
- DB参照・更新はすべて**本番URLに対して行う**（`127.0.0.1` は使わない）
- `curl` + REST API を使用する（`npx supabase db query` は不可）
- 認証情報は `.env.production` の `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` を使用
- 書き込み（INSERT/UPDATE/DELETE）前は対象レコードを SELECT で確認してから実行する

```bash
source .env.production
curl -s "$SUPABASE_URL/rest/v1/<table>?select=*&<filter>" \
  -H "apikey: $SUPABASE_SERVICE_ROLE_KEY" \
  -H "Authorization: Bearer $SUPABASE_SERVICE_ROLE_KEY"
```
```

`general-questions/SKILL.md` 内の「db-access スキルの接続情報を使用」の記述は、
「CLAUDE.md の「DB直接操作の規約」の接続情報を使用」に書き換える。

その後 `.claude/skills/db-access/` ディレクトリを削除する。

## 3. `review` — codex依存を除去・自己レビュー化

### 現状の問題

- Step 2a で `codex review --base develop` を呼んでいるが、このWSL環境では `codex` CLI は使わない
- codexを除くと残りの2チェック（test-guidelines-checker・code-quality-checker）だけになり、一般的なコードレビューの視点が抜ける
- agentファイルが存在しない場合に黙ってスキップする設計で、失敗に気づきにくい

### 改善内容

Step 2a を「Codex Review」から「コードレビューエージェント」に置き換える。
`.claude/agents/` に既存の `test-guidelines-checker.md` / `code-quality-checker.md` があるので、
同じ構成でコードレビュー担当の `code-reviewer.md` を追加する。

#### Step 2 の新構成（3つ並列実行）

| ステップ | エージェント/方法 | チェック観点 |
|---------|-----------------|-------------|
| 2a | `code-reviewer.md`（Agent） | 設計・CLAUDE.mdルール準拠・セキュリティ・ロジック |
| 2b | `test-guidelines-checker.md`（Agent） | テストガイドライン遵守 |
| 2c | `code-quality-checker.md`（Agent） | 可読性・命名・型安全性 |

#### `code-reviewer.md` の追加内容

```markdown
# code-reviewer

CLAUDE.md のルールと設計指針に基づき、変更差分に対してコードレビューを行うエージェント。

## チェック観点

1. **CLAUDE.mdルール準拠**: Button/Icon/Color等のコーディングルール違反がないか
2. **設計指針**: feature構成・Server/Client分離・Repository層の使い方が正しいか
3. **セキュリティ**: SQL injection / XSS / 認証バイパス等のリスクがないか
4. **ロジックの正しさ**: 意図した動作と実装が一致しているか、エッジケースが抜けていないか
5. **不必要な変更の混入**: タスクスコープ外の変更が含まれていないか
```

#### ワークフロー修正

「agentファイルが存在しない場合はスキップ」の記述を削除する。
3ファイルすべての存在が前提であるため、存在しない場合はエラーとして報告する。

#### `--base` オプションの修正

現在 `--base develop` となっているが、このリポジトリのメインブランチは `akitakata/develop`。
エージェントへの差分渡し方法を `git diff akitakata/develop...HEAD` に統一する。

### 実施ファイル

- `.claude/skills/review/SKILL.md` を書き換え
- `.claude/agents/code-reviewer.md` を新規作成

## 4. `parallel-pr` — kawasaki要素の除去

### 現状の問題

`parallel-pr/SKILL.md` と `.claude/agents/worktree-worker.md` の両方に `kawasaki` が残っている。

**`parallel-pr/SKILL.md` 内の kawasaki 参照箇所:**
- `../mirai-gikai-kawasaki-worktree/team-{team}-{x}` （複数箇所）
- `kawasaki/develop` （エージェントプロンプトテンプレート・注意事項）

**`worktree-worker.md` 内の kawasaki 参照箇所:**
- `kawasaki/develop` から指定されたブランチ名で新ブランチを作成
- `gh pr create --base kawasaki/develop`

### 改善内容

| 変更前 | 変更後 |
|--------|--------|
| `../mirai-gikai-kawasaki-worktree/` | `../mirai-gikai-akitakata-worktree/` |
| `kawasaki/develop` | `akitakata/develop` |
| `gh pr create --base kawasaki/develop` | `gh pr create --base akitakata/develop` |

### `bill-registration-akitakata` への展開可能要素

`parallel-pr` の仕組みのうち、bill-registration に転用できる要素を検討した。

**結論: 現時点では転用不要。**

理由:
- bill-registration はDB書き込みオペレーション（コード変更でなく）
- worktreeが活きるのはPRを複数作る場合であり、議案登録には不要
- ただし、AI解説（`bill_contents`）生成の並列化は有効。現在の `process-bills-r7-4.ts` が逐次実行なら、将来的に複数議案のAI生成を並列化する際は `parallel-pr` のエージェント起動パターンを参考にする

**CLAUDE.md との整合:**
CLAUDE.md の `### Worktree必須` セクションも `../mirai-gikai-kawasaki-worktree/` が残っていないか確認し、あれば `akitakata` に修正する。

### 実施ファイル

- `.claude/skills/parallel-pr/SKILL.md` の kawasaki → akitakata 置換
- `.claude/agents/worktree-worker.md` の kawasaki → akitakata 置換

## 5. `general-questions` — スキル再設計

### 現状の問題

現在は**リファレンスドキュメント**として機能しており、「`/general-questions` を呼び出したら何をするか」が明確でない。スキルの定義（呼び出し → アクション）を満たしていない。

内容を分解すると：

| セクション | 性質 | 扱い |
|-----------|------|------|
| UI設計の決定事項 | 過去の意思決定記録 | docs/ に移動 |
| カテゴリ分類テーブル | コードのリファレンス | スキル内に残す（変更時のガイドとして） |
| 関連ファイル一覧 | ファイルマップ | スキル内に残す |
| データ管理（publish_status更新） | **アクション** | スキルの主目的にする |
| AI生成コンテンツの更新ルール | 品質基準ガイドライン | スキル内に残す |
| 今後の課題 | タスク管理 | 削除（Linearで管理） |

### 改善後のスキル設計

**スキル名**: `general-questions`（維持）
**description 更新案**: 「一般質問データの公開・AI生成コンテンツのレビュー・更新を行う。`/general-questions publish`・`/general-questions review` で操作する。」

#### 呼び出しパターン

```
/general-questions publish <session-slug>
  → 指定セッションの全一般質問を publish_status=published に更新

/general-questions review <question-id>
  → 指定IDのtopics（AI生成）を取得してレビュー提示。ユーザー承認後にPATCH実行

/general-questions status <session-slug>
  → 指定セッションの publish_status 一覧を表示
```

#### ワークフロー（publish の例）

```
1. DBから対象セッションの一般質問一覧を取得（publish_status含む）
2. 現在の状態を表示して確認を求める
3. ユーザーが確認したら PATCH で publish_status=published に更新
4. 更新後の状態を再取得して表示
```

#### 残す内容

- カテゴリ分類テーブル（CATEGORY_MAPの変更時に必要）
- 関連ファイル一覧（実装場所の確認用）
- AI生成コンテンツの品質基準（review時に参照）
- `publish_status` 管理コマンド（アクションの核心）

#### docs/ に移動する内容

- UI設計の決定事項（テーマ別ビュー採用理由・個人ページトグル採用理由）
  → `docs/akitakata/general-questions-ui-decisions.md` として保存

#### 削除する内容

- 「今後の課題」セクション（Linearで管理するべき情報）

### 実施ファイル

- `.claude/skills/general-questions/SKILL.md` を全面書き換え
- `docs/akitakata/general-questions-ui-decisions.md` を新規作成（UI設計記録を移管）
